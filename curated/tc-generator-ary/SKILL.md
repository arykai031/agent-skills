# Test Case Generator ARY

基于需求文档（PRD/Spec）或功能描述，自动生成面向功能测试的结构化 Markdown 测试用例。

---

## 1. 核心原则

### 用例本质

```
测试用例 = 前置条件 + 操作步骤 + 预期结果
```

每条用例必须独立可执行，他人拿到用例无需额外解释即可执行。

### 用例语言：业务语言优先 ⭐

测试用例的读者是测试人员和业务人员，**严禁**在用例内容中出现以下技术标识符：

| 禁止 | 原因 | 正确做法 |
|------|------|----------|
| 数据库字段名 | 测试人员不关心表结构 | 使用界面上的字段标签 |
| 枚举常量/代码值 | 无法直接理解含义 | 使用对应的中文描述 |
| 技术变量名 | 如 `isOverdue`、`overdue` | 使用"是否超时"、"超时状态" |
| API 参数名 | 非接口测试不需要 | 使用参数对应的业务含义 |
| `NULL`、`TRUE/FALSE` | 技术术语 | 使用"为空/未填写"、"是/否" |

**关键转换规则**：

1. **从 PRD 中提取字段映射**：PRD 通常在"数据影响"或"字段说明"章节给出了字段名→中文名的对照表。生成用例前务必先提取这些映射，用例中**始终使用中文名**。

2. **状态值必须翻译**：`borrow_status = '5'` → "借出单已完全借出"；不要写成 "borrow_status='5'"。如果 PRD 中有状态码与含义的对照表，使用其含义。

3. **枚举型必须翻译**：`BORROW_TIMEOUT("4")` → "借出超时预警类型"；不要写成"预警类型为 BORROW_TIMEOUT"或"类型为 4"。

4. **布尔/标记字段用自然语言**：`isOverdue='1'` → "筛选已超时的单据"；`overdue=true` → "显示为超时状态"。

5. **空值用自然语言**：`require_return_time IS NULL` → "要求还入时间为空（未填写）"；`field IS NOT NULL` → "已填写 XX"。

**转换示例**：

| ❌ 错误写法（技术标识符） | ✅ 正确写法（业务语言） |
|--------------------------|------------------------|
| `borrow_status='5' 的借出单` | 已完全借出的借出单 |
| `require_return_time < now()` | 要求还入时间已过期 |
| `isOverdue='1' 筛选` | 筛选已超时单据 |
| `BORROW_TIMEOUT 类型配置` | 借出超时预警类型配置 |
| `status='0' 的公告` | 未处理的预警公告 |
| `requireReturnTime 为空` | 要求还入时间未填写 |
| `overdue 字段返回 true` | 借出单显示为超时状态 |
| `borrow_status IN ('4','5')` | 借出单处于部分借出或完全借出状态 |

### 优先级与比例

| 优先级图标 | 含义 | 说明 |
|------------|------|------|
| 1️⃣ | 必测 | 核心主流程，阻断性缺陷会导致功能不可用 |
| 2️⃣ | 重要 | 重要分支、主要业务规则校验 |
| 3️⃣ | 一般 | 边界条件、异常场景、次要功能 |
| 4️⃣ | 可选 | 体验优化、极端边界，时间充裕时才执行 |

**目标比例：1️⃣ : 2️⃣ : 3️⃣ ≈ 2 : 4 : 4**（即 1️⃣ 占 20%，2️⃣ 占 40%，3️⃣ 占 40%，4️⃣ 按需追加）

> **为什么是这个比例？** 1️⃣ 覆盖核心路径确保主流程不出问题；2️⃣ 覆盖主要分支和校验确保功能完整；3️⃣ 覆盖边界和异常确保健壮性。比例可根据项目阶段调整（如提测初期 1️⃣/2️⃣ 占比更高）。

### 执行状态

每条测试用例必须使用 Obsidian 待办任务格式：未执行时为 `- [ ]`，执行完成后勾选为 `- [x]`。不要在行尾追加“通过”或“未通过”选项。

## 2. 五步工作流

### Step 0：前置成果检索 ⭐

**在开始需求解析之前**，汇总所有 Spec 的共享信息，确保用例生成基于完整的全局视角。

> **注意**：确认与同步工作由 `tc-pipeline` 调度器完成。当通过调度器调用本技能时，Spec 已是定稿状态，直接从 0.1 开始即可。当独立调用本技能时，应先检查 Spec 中是否有未闭环标记，有则停止并提示用户先通过调度器完成确认。

#### 0.1 识别输入材料类型

**情况 A — 输入是 PRD 精简（推荐）**

PRD 精简是 `prd-splitter` 拆分后的产物，其 frontmatter 中的 `specs` 字段记录了所有关联 Spec 的路径和摘要。**优先使用 PRD 精简作为入口**，因为它是唯一知道"有哪些 Spec"的权威来源。

流程：
1. 读取 PRD 精简的 frontmatter，提取 `specs` 列表
2. 根据 `specs[].file` 逐个读取所有 Spec 文件
3. 从 `specs[].summary` 快速了解各 Spec 的范围，结合 `specs[].type` 决定分析重点

如果 PRD 精简的 frontmatter 中没有 `specs` 字段，说明是旧版拆分产物，回退到情况 B。

**情况 B — 输入是 Spec 文件或目录（无 PRD 精简）**

1. 先扫描同级目录或父目录，查找是否存在 `PRD精简_*.md`
2. 如果找到 → 读取其 `specs` frontmatter，按情况 A 处理
3. 如果找不到 → 按以下方式处理：
   - 输入是**目录**：扫描目录下所有 Spec 文件，逐份读取
   - 输入是**单个 Spec**：检查其 frontmatter 的 `source_docs` 和 `mapped_rules`，提取规则编号供后续 Step 1 使用

**情况 C — 输入是单个 PRD 或功能描述**

跳过 Step 0，直接进入 Step 1。

---

#### 0.2 汇总前置成果

**情况 A — 有 PRD 精简**

根据 `specs` frontmatter 列表，逐份读取 Spec，完成以下汇总：

1. **提取共享状态机**：汇总各 Spec 的"状态机"章节，合并为完整的状态流转图。检查是否有跨 Spec 的状态转换被遗漏（如"暂停申请中 → 取消申请中"可能只在任务控制 Spec 中定义，但异步执行 Spec 也需要它）
2. **提取共享数据模型**：汇总各 Spec 的"数据模型变更"章节，合并为完整的表结构清单。标注哪些表被多个 Spec 引用
3. **汇总 BR/AB 规则全集**：从各 Spec 的 frontmatter 中提取 `mapped_rules`，合并去重，检查是否有编号跳跃或遗漏
4. **汇总 API 端点清单**：从各 Spec 的"API 契约"章节提取所有端点，建立端点→所在 Spec 的映射表
5. **汇总验收标准全集**：从各 Spec 的"验收标准"章节提取所有 AC 条数，按模块统计
6. **提取"本次不做"范围**：从 PRD 精简的"范围决策 → 本次不做"章节提取，用于后续排除无效用例

**情况 B — 无 PRD 精简**

1. 输入是**目录**：扫描目录下所有 Spec 文件，逐份读取，完成上述 1-5 项汇总
2. 输入是**单个 Spec**：提取其 `mapped_rules`，供后续 Step 1 使用

---

输出一份**前置成果索引**（不写入文件，内部使用）：

```
前置成果索引（来源：PRD精简_xxx.md 的 specs 列表）：
├── Spec 文件清单：5 份

│   └── 前端交互与通知.md → 轮询/通知 + 3 个页面 + 17 条 AC
├── 共享状态机：9 个状态（汇总自 3 份 Spec）
├── 共享数据模型：2 张新表 + 1 张变更表 + 3 个枚举扩展
```

### Step 1：需求解析

**输入**：PRD / Spec / 需求文档 / 接口文档 / 用户的自然语言描述

**分析内容**：
1. 提取功能模块清单 → 识别核心路径与辅助功能
2. 标注业务规则和约束条件
3. 识别角色、权限、状态转换等关键维度
4. **提取字段映射表**：从 PRD 的"数据影响"/"字段说明"等章节提取字段名→中文名的映射关系（如 `borrow_status` → "借出状态"），后续用例中**严禁使用原始字段名**

**材料类型适配**：

| 材料类型 | 分析重点 | 输出侧重 | 说明 |
|----------|----------|----------|------|
| PRD 精简（推荐） | 读取 `specs` frontmatter → 逐份读取 Spec → 使用 Step 0 汇总的共享状态机、数据模型、BR/AB 全集、API 清单 | 功能用例 + 跨模块集成用例为主 | 优先使用 PRD 精简作为入口，其 `specs` 列表是权威的 Spec 清单 |
| PRD（原始） | 业务背景、功能点、用户故事 | 功能用例为主 | - |
| 单份 Spec | I/O定义、验收标准、约束 | 异常+边界用例为主 | 检查 frontmatter 的 source_docs，确认是否需要 PRD 精简 |
| 接口文档 | 请求参数、响应结构、错误码 | 参数校验+异常用例为主 | - |
| 流程图 | 分支路径、角色权限、状态机 | 路径覆盖+状态覆盖 | - |

**⚠️ 模糊需求处理（重要）**：

遇到以下情况时，**必须停止生成**，**立即向用户提问**确认，确认完成后再继续：
- 功能描述含糊（如"支持搜索"但未说明搜索字段）
- 业务规则不明确（如"按比例分配"但未说明分配逻辑）
- 状态转换条件缺失（如"审核通过后…"但未说明谁可以审核）
- 权限范围模糊（如"管理员可以操作"但未说明哪些角色算管理员）
- **Step 0.2 未闭环的确认项**：如果 Step 0.2 扫描到未闭环标记但用户未确认就跳过了，这里需再次提醒

提问模板：
```
我在分析需求时发现以下不明确的地方，需要确认后再生成用例：
1. [问题1]
2. [问题2]
...
```

### Step 2：三层用例生成

按以下顺序推导，确保覆盖全面。每层的用例数量参考目标比例分配。

#### 第一层 — 功能用例（正向流程）

目标：覆盖所有「正常走通」的场景。

每个功能点生成 2-3 个正常场景，参考以下维度：
- **核心流程** → 1️⃣（如：完整走完新增→保存→列表显示）
- **重要功能分支** → 2️⃣（如：编辑后保存、带条件查询）
- **辅助功能** → 3️⃣（如：重置按钮、分页切换）

```markdown
### [TC-模块缩写-功能-001] 新增配置-保存成功

- [ ] 1️⃣  已登录;有菜单权限 | 填写所有必填项;点击保存 | 提示"保存成功";列表刷新显示新增数据
- **数据依赖**：无
```

#### 第二层 — 异常用例（逆向校验）

基于第一层的功能用例，**逐条推导**其异常分支。每个正常操作对应 1-2 个异常场景。

| 异常类型 | 推导思路 | 示例 |
|----------|----------|------|
| 参数缺失 | 必填字段逐一留空 | 用户名为空时点击登录 |
| 格式错误 | 字段类型约束违反 | 整数字段输入中文 |
| 权限不足 | 不同角色/状态组合 | 普通用户访问管理员接口 |
| 资源不存在 | 使用已删除/不存在的ID | 编辑已删除的数据 |
| 业务规则冲突 | 违反唯一性/状态约束 | 重复提交相同编码的数据 |
| 并发冲突 | 多用户同时操作 | 两人同时编辑同一条数据 |

#### 第三层 — 边界用例（极端条件）

覆盖「能输入什么极值」和「系统如何处理极端情况」。

| 边界类型 | 推导思路 | 示例 |
|----------|----------|------|
| 空值 | NULL、空字符串、空数组、空列表 | 可选字段留空提交 |
| 极值 | 最大/最小长度、最大/最小数量、最大/最小值 | 输入255字符的用户名 |
| 特殊字符 | SQL注入、XSS、HTML标签、emoji | 用户名为 `<script>alert(1)</script>` |
| 重复提交 | 快速连续点击 | 保存按钮连续点击5次 |
| 并发操作 | 同时对同一数据操作 | 两人同时删除同一条数据 |
| 超时/断网 | 请求超时、网络中断 | 保存过程中断开网络 |
| 跨模块联动 | 上下游模块边界 | 入库单已关联质检，再修改入库设置 |

---

### Step 3：覆盖分析

生成用例后，系统性检查覆盖率（**不需要写入输出文件**）：

| 检查项 | 检查内容 | 如何处理遗漏 |
|--------|----------|--------------|
| 页面覆盖 | 所有页面/弹窗是否有对应用例 | 补充该页面/弹窗的用例 |
| 角色覆盖 | 所有用户角色是否都有对应权限用例 | 按角色×操作矩阵补充 |
| 状态覆盖 | 关键状态转换是否覆盖（如：待审核→已审核） | 补充状态转换用例 |
| 路径覆盖 | 主流程各分支是否都有正向+逆向用例 | 画流程图对照补充 |
| 数据覆盖 | 列表空/有数据、权限有/无等组合 | 补充数据条件组合用例 |

**如有遗漏**：补充对应用例，并在回复中说明补充了哪些场景以及原因。

---

### Step 4：格式化输出

输出标准 Markdown 格式，以 Obsidian 待办任务记录测试执行状态。不要输出通过/未通过确认项。

> 当前格式为三段式待办任务；如需转换为 Excel，先确认 `TC-md-to-excel` 已支持此格式。

#### 输出格式规范

```markdown
---
title: 测试用例-[功能名称]
author: [你的名字或 aryKai]
created: YYYY-MM-DD
tags: [doc/test-case, 项目名/版本, 模块名]
source: [需求文档来源，如 Spec-xxx.md]
---

# [所属模块名称]

---

## [功能点名称]

### [TC-功能缩写-序号] [用例标题]

- [ ] 1️⃣  前置条件1;前置条件2 | 操作步骤1;操作步骤2 | 预期结果1;预期结果2
- **数据依赖**：[无 / 依赖的用例编号，如 TC-QCM-CL-013]

### [用例标题]

- [ ] 2️⃣  前置条件 | 操作步骤 | 预期结果
```

#### 字段说明

| 符号/格式 | 含义 | 注意事项 |
|-----------|------|----------|
| `#` | 所属模块（一级标题） | 整个文件只有一个 `#` 标题 |
| `##` | 功能点（二级标题） | 一个模块下有多个功能点 |
| `###` | 用例标题（三级标题） | 建议包含用例编号，如 `[TC-CL-001]` |
| `1️⃣` / `2️⃣` / `3️⃣` / `4️⃣` | 优先级 | 每条用例必须且只能使用一个图标，详见第一节 |
| `- [ ]` | 待办任务 | 未执行时保留；执行完成后勾选为 `- [x]` |
| `\|` | 字段分隔符 | 仅分隔前置条件、操作步骤、预期结果 |
| `;` | 同字段内多条内容分隔符 | 如 `已登录;有菜单权限` 表示两个条件同时满足 |
| `**数据依赖**` | 数据依赖说明 | 见下方说明 |

#### 数据依赖字段

`**数据依赖**` 用于说明执行当前用例前，需要先执行哪些用例来准备测试数据。

规则：
- 无依赖时写 `无`
- 有依赖时写依赖的用例编号，多个用逗号分隔，如 `TC-CL-013, TC-CL-024`
- 依赖「系统初始化数据」时写 `系统初始化`
- 放在用例内容的下一行（与待办任务行之间不插空行）

#### 完整输出示例

```markdown
---
title: 测试用例-用户登录
author: aryKai
created: 2026-05-09
tags: [doc/test-case, wms/v3.0.6, 登录]
source: Spec-登录模块.md
---

# 用户登录

---

## 登录模块

### [TC-LOGIN-001] 正常登录成功

- [ ] 1️⃣  用户名正确;密码正确;用户已激活 | 输入用户名;输入密码;点击登录 | 登录成功;跳转首页;记录登录日志
- **数据依赖**：无

### [TC-LOGIN-002] 用户名为空校验

- [ ] 2️⃣  用户名为空;密码正确 | 留空用户名;输入密码;点击登录 | 提示"用户名不能为空";焦点定位到用户名输入框
- **数据依赖**：无

### [TC-LOGIN-003] 密码错误三次锁定

- [ ] 2️⃣  用户名正确;连续输入错误密码2次;第3次输入错误密码 | 输入正确用户名;输入错误密码;点击登录（重复3次） | 第3次提示"账号已锁定";账号状态变为锁定
- **数据依赖**：无

### [TC-LOGIN-004] 锁定后使用正确密码登录

- [ ] 3️⃣  账号已被锁定 | 输入锁定账号的用户名;输入正确密码;点击登录 | 提示"账号已锁定，请联系管理员"
- **数据依赖**：TC-LOGIN-003
```

## 3. 测试点快速清单

生成用例时，参考以下清单确保不遗漏重要测试点。

### 通用测试点

| 类别 | 测试点 | 说明 |
|------|--------|------|
| **入口权限** | 功能可见性、权限控制、登录校验、路由校验 | 入口与访问控制 |
| **页面元素** | 布局、必填标识、默认值、字段类型、只读/可编辑状态 | 界面显示正确 |
| **联动关系** | 级联联动（如仓库→库区）、状态联动、清空联动 | 上下级交互正确 |
| **校验规则** | 必填、格式、长度、范围、唯一性、业务规则 | 数据校验有效 |
| **操作功能** | 新增、编辑、删除、查询、重置、导入、导出、状态切换 | 增删改查完整 |
| **结果展示** | 成功提示、错误提示、列表刷新、分页、排序 | 结果呈现正确 |

### 业务测试点

| 类别 | 测试点 | 说明 |
|------|--------|------|
| **业务规则** | 主流程、分支流程、边界值、组合条件匹配 | 业务逻辑正确 |
| **数据处理** | 数据存储、数据计算、数据转换、数据关联、事务回滚 | 数据处理准确 |
| **定时任务** | 触发时机、参数读取、执行日志、异常处理 | 任务执行可靠 |

### 异常边界点

| 类别 | 测试点 | 说明 |
|------|--------|------|
| **异常场景** | 空数据、超大数据、并发操作、重复操作、网络异常、服务重启 | 异常处理得当 |
| **边界条件** | 数值边界、字符边界、日期边界、状态边界、数量边界 | 边界处理正确 |
| **性能安全** | 响应时间、操作日志、数据权限、SQL注入、XSS | 非功能满足 |

## 5. 输出检查清单

生成用例后，按以下清单自查（**自查内容不需要写入输出文件**）：

### 前置检查（Step 0）

- [ ] 多 Spec 项目：已完成共享状态机、共享数据模型、BR/AB 规则、API 端点、AC 的汇总
- [ ] 所有 Spec 中无"待确认""待补充""需补充""若不支持""若现仅"等未闭环标记（若有，说明确认同步未完成，应通过 tc-pipeline 执行）

### 用例内容检查

- [ ] 每条验收标准/需求点至少对应 1 条测试用例
- [ ] 正向用例覆盖主流程（核心路径标记为 1️⃣）
- [ ] 异常用例覆盖所有校验规则（必填、格式、长度、唯一性等）
- [ ] 边界用例覆盖所有输入字段的极值条件
- [ ] 每条用例的「前置条件」明确且可复现
- [ ] 每条用例的「操作步骤」无歧义，按顺序可执行
- [ ] 每条用例的「预期结果」可验证（有明确的现象或提示）
- [ ] 优先级分配合理（1️⃣/2️⃣/3️⃣ 比例接近 2:4:4）
- [ ] **用例中无数据库字段名、枚举代码、技术变量名**，全部使用业务可读的中文描述（如"已完全借出"而非"borrow_status='5'"）
- [ ] 「数据依赖」字段已填写（有依赖的用例必须标注）
- [ ] 每条用例均以 `- [ ] 优先级图标` 开头，且仅包含前置条件、操作步骤、预期结果三个字段

### 跨 Spec 覆盖检查（多 Spec 项目）

- [ ] 状态机覆盖：所有合法状态转换路径至少 1 条用例，所有非法转换路径至少 1 条异常用例
- [ ] 数据一致性覆盖：跨表字段（如 async_api_task.priority = allocation_progress.task_priority）有对应的断言用例
- [ ] 跨模块流程覆盖：存在端到端场景用例（如"提交任务 → 暂停 → 恢复 → 查询进度 → 终态通知"）
- [ ] BR/AB 规则全集：每条业务规则和异常边界至少对应 1 条用例

## 6. 协作说明

### 配合流程

```
prd-writer / prd-splitter → test-case-generator-ary → TC-md-to-excel → 测试执行
        ↑ 生成需求              ↑ 生成用例                 ↑ 转Excel        ↓ 结果回填
```

### 输出应用

生成的 Markdown 测试用例可直接用于：
- 测试用例评审（Markdown 便于 Review）
- 测试执行记录（在 Obsidian 中勾选待办任务）
- 缺陷定位参考（用例编号可关联到 Bug 管理系统）
- 回归测试套件（复选框记录用例是否已执行）

### 与 TC-md-to-excel 的衔接

本技能改用 Obsidian 待办任务格式，与旧版 `TC-md-to-excel` 的解析规则不完全兼容。需要导出 Excel 时，先更新并验证转换器对以下格式的支持：
- `#` → 所属模块（Excel 的 B 列）
- `##` → 功能点（Excel 的 C 列）
- `###` → 用例标题（Excel 的 E 列，编号建议保留在标题中）
- `1️⃣` / `2️⃣` / `3️⃣` / `4️⃣` → 优先级（Excel 的 D 列）
- `|` 分隔的三个字段 → 前置条件/操作步骤/预期结果（Excel 的 F/G/H 列）
- `- [ ]` / `- [x]` → 用例是否已执行（可映射至 Excel 的执行结果列）
- `**数据依赖**` → 不会被解析进 Excel，但保留在 Markdown 中供执行参考
