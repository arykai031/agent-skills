# PRD Splitter

接收一份完整 PRD，将其拆分为两份文档：
- **PRD精简**：保留"为什么做、做什么、谁来决策"的对齐层，面向团队
- **Spec**：提取"怎么做、边界在哪、怎么验收"的执行层，面向 AI

## 前置条件：输入材料准备

prd-splitter 的输入是结构化的 PRD 文档。如果输入是**原始开发设计文档**（纯技术视角，含类名/代码逻辑/SQL等），必须先经过 `devDoc-to-test-prd` 技能翻译为测试视角的 PRD。

**翻译前后对比**（以 WMS 出库订单波次分配为例）：

| 原始设计文档 | 翻译后 PRD |
|-------------|-----------|
| 12 章纯后端架构设计（Handler、CAS、XXL-Job、SQL 表定义） | 5 层结构：功能概述 → 业务规则 BR-01~BR-25 → 状态流转 → 数据影响 → 异常边界 AB-01~AB-17 |
| 代码级描述："AsyncApiTaskExecuteThread 扫描 status=1 的任务" | 业务语言："定时调度器扫描待处理状态的任务" |
| 裸数字状态码：1/2/3/4/5/6/7/8/9 | 中文状态对照表：待处理/处理中/全部成功/… |

**流程**：
```
原始设计文档 → devDoc-to-test-prd → 结构化PRD (含🚧/📌标记) → 用户确认🚧缺口 → 定稿PRD → prd-splitter
```

如果输入已经是结构化 PRD（如你们手动整理的 `prd-出库订单波次分配异步进度条.md`），跳过 devDoc-to-test-prd，直接进入 prd-splitter。

## 核心原则

PRD 和 Spec 的本质区别是**面向对象不同**：
- PRD 写给人看，依赖读者的专业判断来补全细节
- Spec 写给 AI 执行，不能留任何需要猜测的空间

拆分不是复制粘贴，而是**重新提炼**：

PRD 里"好看一点""功能完整"这类描述，在 Spec 里必须转化为可验证的具体标准。

---

## 第零步：识别 PRD 类型

在动笔前，先判断 PRD 属于哪种类型。不同类型的 PRD，Spec 的字段结构不同。

### 类型判断规则

| 特征 | 类型 | Spec 关键字段 |
|------|------|-------------|
| 大量页面交互描述、UI 草图、表单字段 | **前端交互型** | I/O（表单模式）、AC（UI验证模式） |
| API 端点定义、数据库表变更、状态机、调度器、枚举扩展 | **后端服务型** | API契约、数据模型变更、状态机、依赖项 |
| 两者都有，且前端页面 ≥2 个 + 后端接口 ≥3 个 | **混合型** | 分别拆为前端 Spec + 后端 Spec |
| 以数据报表、导入导出、数据清洗为主 | **数据处理型** | I/O（文件模式）、数据模型变更、AC（数据断言模式） |

**判断方法**：扫描原 PRD 的章节标题和内容关键词，统计以下信号：

| 信号 | 指向类型 |
|------|---------|
| 页面截图/草图、UI 组件、交互流程、前端状态 | 前端交互型 |
| API 端点、数据库表/字段、枚举、定时任务、状态机、Handler | 后端服务型 |
| SQL、存储过程、数据导入导出、报表模板 | 数据处理型 |

如果原 PRD 同时有"设计方案文档"（如设计文档 + 整理后的 PRD），优先以**设计文档**的章节结构作为类型判断依据，因为设计文档通常更完整地覆盖了后端架构。

---

## 第一步：读懂原 PRD

读完后，在动笔前先完成三件事：

1. **列出需求点清单**：原 PRD 有几个独立功能点？每个需要生成一份 Spec
2. **标记模糊项**：哪些描述在 PRD 里是模糊的（"好看""完整""合理"），需要在 Spec 里转化或标注"待确认"
3. **识别已有结构化信息**：原 PRD 是否已经包含以下内容？有则直接提取，不要重新发明：
   - 业务规则编号（如 BR-01、BR-02）→ 直接映射到 Spec 的约束和验收标准
   - 异常边界编号（如 AB-01、AB-02）→ 直接映射到 Spec 的异常覆盖
   - 状态码值与中文对照表 → 直接映射到 Spec 的状态机
   - 数据表字段定义表 → 直接映射到 Spec 的数据模型变更
   - API 接口定义（入参/出参）→ 直接映射到 Spec 的 API 契约

---

## 第二步：生成 PRD精简

**每节的提炼要点：**

### 背景与目标

- 保留"为什么"的论述，压缩掉实现细节
- 目标必须带指标（如果原 PRD 有的话），没有指标的目标写"【待补充量化指标】"

### 范围决策

- "不做什么"和"做什么"同等重要，必须都写出来
- 有时原 PRD 没有显式写"不做"，需要根据功能边界反推并补充

### 关键决策记录

- 从评审记录、功能备注、"暂不"/"后续"等措辞中提取决策
- 格式：【决策】xxx 【原因】xxx

### 待确认事项

- 原 PRD 中标注"待确认"的内容直接搬过来
- 原 PRD 中模糊但没有标注的内容，提炼后也放这里，并注明"原 PRD 未明确，建议确认"

---

## 第三步：生成 Spec

**每个独立功能点生成一份 Spec**

### 判断需要几份 Spec

原则：**一个 Spec 对应一个可独立交付、独立验收的任务单元**。

#### 前端交互型 PRD 的拆分规则

| 情况 | 处理方式 |
|-----|---------|
| 前端页面 + 后端接口 | 通常拆成独立 Spec（前端/后端各一份），除非强耦合 |
| 多个页面但同一功能流 | 可以合并为一份，但 I/O 按页面分开描述 |
| 后台配置 + 前台展示 | 拆成两份（运营配置 Spec + 用户侧 Spec） |

#### 后端服务型 PRD 的拆分规则

| 情况 | 处理方式 | 示例 |
|------|---------|------|
| 多个 API 端点 + 一张新表 | 合并为一份，API 契约按端点分开描述 | 进度查询 + 明细查询 + 列表查询 → 1 份"查询模块 Spec" |
| 状态机 + 调度器 + 执行器 | 合并为一份，按子模块分开描述 | 任务提交 + 调度执行 + 状态流转 → 1 份"核心执行 Spec" |
| 控制操作（暂停/恢复/取消） | 独立一份，因为涉及独立的接口和状态校验 | 1 份"任务控制 Spec" |
| 通知/推送/消息 | 独立一份，因为通常依赖外部系统 | 1 份"通知集成 Spec" |
| 前端页面（≥2 个独立页面） | 独立一份，参照前端交互型 Spec | 1 份"前端交互 Spec" |

**结果**：后端服务型 PRD 通常产出 2-5 份 Spec，而非 1 份或 10+ 份。

---

### Spec 字段结构（按 PRD 类型）

#### 所有类型共有的基础字段

**目标（Goal）**：
- 不写"做一个xx功能"，写"用户能通过xxx完成xxx，达到xxx"
- 必须包含：谁 + 怎么做 + 达成什么

**边界（Scope）**：
- 从原 PRD 的功能点拆分表格 + 备注中提取
- 明确写"本次不包含"，防止 AI 过度实现

**约束（Constraints）**：
- 技术约束：使用什么框架、组件库、接口规范
- 安全约束：数据存储方式、权限控制
- 设计约束：对应设计稿的哪个页面（标注蓝湖链接或页面名）

**非目标（Non-Goals）**：
- 来自两个来源：
  - 原 PRD 明确说不做的
  - 容易被误解为"应该有"但其实本次不做的
- 写非目标是为了防止 AI 顺手加功能

---

#### 前端交互型额外字段

**输入输出（I/O）— 表单模式**：
- 字段级别的精度：字段名、类型、长度、必填、校验规则
- 输出覆盖所有状态：成功 / 失败 / 网络异常 / 空状态
- 如果原 PRD 只写了"登录成功跳转"，需要补全：跳转到哪个路径、携带什么参数

**验收标准（AC）— UI 验证模式**：
- 每条都必须能用"打开页面/调接口"来验证，不允许出现"体验良好""显示正确"这类词
- 转化示例：
  - PRD写："登录成功后跳转" → Spec写："✅ 输入正确邮箱密码点击登录，3秒内跳转到 /dashboard"
  - PRD写："显示错误提示" → Spec写："✅ 输入错误密码提交后，按钮下方显示红色文字'邮箱或密码错误'，按钮恢复可点击"
  - PRD写："记住我功能" → Spec写："✅ 勾选记住我后，token 存储在 httpOnly cookie 中，关闭浏览器重新打开仍保持登录状态"

---

#### 后端服务型额外字段

**数据模型变更（Data Model）**：

从原 PRD 的"数据影响"、"数据模型设计"、"落地改造"等章节提取。必须覆盖：

1. **新增表**：每张新表的完整字段定义（字段名、类型、说明、是否查询条件、是否下拉筛选）
2. **变更表**：在现有表上新增/修改的字段（字段名、类型、变更前 → 变更后）
3. **枚举扩展**：新增/修改的枚举值（枚举名、码值、中文含义、说明）
4. **索引与约束**：如果有明确提及

格式示例：
```
### 新增表：allocation_progress
| 字段 | 类型 | 说明 | 查询属性 |
|------|------|------|---------|
| progress_id | bigint | 主键，自增 | - |
| biz_type | char(2) | 1=出库订单，2=波次 | 🔍▼ |
| status | char(2) | 进度状态 | 🔍▼ |

### 枚举扩展：AsyncApiTaskStatus
| 码值 | 含义 | 说明 |
|------|------|------|
| 5 | 暂停申请中 | 新增 |
| 6 | 已暂停 | 新增 |
```

**API 契约（API Contracts）**：

从原 PRD 的"后端接口设计"章节提取，每个端点一个子节。必须覆盖：

1. **方法 + 路径**：如 `POST /allocation/progress/{taskId}/pause`
2. **入参**：JSON Schema 或字段表（字段名、类型、必填、默认值、说明）
3. **出参**：JSON Schema 或字段表，必须覆盖成功和异常两种返回
4. **状态码**：200 返回什么、400/409/500 各返回什么
5. **业务校验规则**：什么情况下拒绝（如"状态不为1或2时拒绝暂停"）

格式示例：
```
### POST /allocation/progress/{taskId}/pause — 暂停任务

入参：
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| reason | varchar(512) | 否 | 暂停原因 |

出参（成功）：
```json
{ "taskId": 12345, "status": "5", "message": "已接收暂停请求，当前明细完成后生效" }
```

出参（失败）：
```json
{ "code": 400, "message": "当前任务状态不允许暂停" }
```

业务校验：
- 仅允许状态为 1（待处理）或 2（处理中）的任务暂停
- 状态为 1 时直接变为 6（已暂停）；状态为 2 时变为 5（暂停申请中）
```

**状态机（State Machine）**：

从原 PRD 的"状态流转"章节提取。必须包含：

1. **状态码值对照表**：所有状态的码值、中文含义、说明
2. **状态流转图**：用 ASCII 图或 Mermaid 描述状态之间的合法转换
3. **每个状态下的可用操作**：哪些操作在当前状态下允许
4. **终态列表**：哪些状态是终态（不可再变）

格式示例：
```
### 异步任务状态（9 个状态）

| 码值 | 含义 | 类型 |
|------|------|------|
| 1 | 待处理 | 非终态 |
| 2 | 处理中 | 非终态 |
| 3 | 全部成功 | 终态 |
| 8 | 已取消 | 终态 |

### 状态 → 可用操作映射

| 状态 | 暂停 | 恢复 | 取消 | 调整优先级 |
|------|------|------|------|-----------|
| 1-待处理 | ✅ | ❌ | ✅ | ✅ |
| 2-处理中 | ✅ | ❌ | ✅ | ❌ |
| 6-已暂停 | ❌ | ✅ | ✅ | ✅ |
```

**依赖项与集成点（Dependencies）**：

列出本功能依赖的现有系统/表/接口/组件，防止 AI 不知道需要改哪里。包括：

1. **复用的现有组件**：如"复用 AsyncApiTaskExecuteThread"、"复用 OrderHeaderServiceImpl 分配逻辑"
2. **需要扩展的现有枚举/表**：如"扩展 AsyncApiTaskType 枚举"、"AsyncApiTask 表新增 priority 字段"
3. **依赖的外部系统**：如"复用现有通知管理"、"依赖 XXL-Job 调度器"
4. **需要新增的类/接口**：如"新增 IAllocationProgressService"、"新增 OrderAsyncAssignHandler"

**验收标准（AC）— 后端验证模式**：

使用以下验证模板，每条 AC 必须可操作：

| 验证类型 | 模板 | 示例 |
|---------|------|------|
| API 断言 | `调 POST /xxx，传入 {params}，断言 status=200，响应 {field} = {value}` | `调 POST /allocation/progress/1/pause，传入 {"reason":"测试"}，断言 status=200，响应 status="5"` |
| 数据库断言 | `查表 {table}，条件 {where}，断言 {field} = {value}` | `查表 allocation_progress，条件 task_id=1，断言 status="6"，processed_count 不变` |
| 调度器行为 | `等待 XXL-Job 下一轮扫描后，查表 {table}，断言 {condition}` | `等待调度器扫描后，查表 async_api_task 条件 task_id=1，断言 status="2"` |
| 状态一致性 | `操作 {action} 后，查 {table1}.{field1} 和 {table2}.{field2}，断言值一致` | `调整优先级为 9 后，查 async_api_task.priority 和 allocation_progress.task_priority，断言均为 9` |
| 并发安全 | `并发 {N} 个请求同时 {action}，断言只有 1 个成功，其余返回 {error_code}` | `并发 3 个请求同时暂停同一任务，断言只有 1 个返回成功，其余返回 400` |

转化示例：
- PRD写："暂停操作仅允许状态为待处理或处理中的任务" → Spec写："✅ 调 POST /pause 传入 taskId=已暂停任务，断言 status=400，message 包含'不允许暂停'"
- PRD写："调度器在真正执行前通过乐观锁校验状态" → Spec写："✅ 并发场景：前端暂停 taskId=1 的同时调度器拉取到 taskId=1，断言调度器 CAS 更新失败，taskId=1 不会被拉起执行"
- PRD写："所有明细处理完毕后根据成功/失败统计给出任务终态" → Spec写："✅ 10条明细中 3 条分配失败，断言 task 终态为 9（部分成功），allocation_progress.fail_count=3"

**禁止使用的模糊词**（与前端 AC 相同）："正常""正确""合理""良好""完整""体验良好""显示正确"。出现则替换。

---

#### 数据处理型额外字段

**输入输出（I/O）— 文件模式**：
- 输入文件：格式（CSV/Excel/JSON）、编码、分隔符、表头行、必填列
- 输出文件：格式、命名规则、输出路径、是否覆盖已有文件

**数据模型变更（Data Model）**：同后端服务型

**验收标准（AC）— 数据断言模式**：
- 使用"输入 N 条数据 → 执行 → 断言输出文件/数据库中有 M 条，字段 X = Y"的模式
- 示例："✅ 输入 100 条出库单 CSV，执行导入，断言 allocation_progress_detail 表新增 100 条记录，status 均为 0"

## 第四步：输出前检查

输出两份文档前，做一致性检查：

### PRD精简检查

- 每个"待确认"是否都有对应的负责人？（没有就写"待指定"）
- "不做什么"是否有覆盖所有容易被误解为"应该有"的功能？
- 关键决策是否都有记录原因，而不只是结论？
- **待确认事项表格是否位于 PRD 精简中**：确认结果只写入 PRD 精简，不写入 Spec。Spec 中的同步由下游技能（TC-generator-ary）在运行时自动完成

### Spec检查（通用）

- 验收标准里有没有出现"正常""正确""合理""良好"这类不可验证的词？有则替换掉
- 非目标是否明确排除了"AI 最容易顺手做的功能"？

### Spec检查（后端服务型额外）

- 数据模型变更是否覆盖了：新增表、变更表、枚举扩展三项？如果原 PRD 有数据影响章节但 Spec 遗漏了任一项，补上
- API 契约是否每个端点都覆盖了：成功响应 + 至少一种失败响应 + 业务校验规则？
- 状态机是否每个状态都有明确的"可用操作"列表？终态是否标注？
- 依赖项是否列出了所有需要修改的现有代码位置（类名/表名）？
- 如果原 PRD 有 BR/AB 编号规则，Spec 的 AC 是否每条 BR 至少对应一条 AC？

### 两份文档之间的检查

- PRD精简里的每个需求点，Spec 里是否都有对应的文档？
- PRD精简里标注"待确认"的项，Spec 里是否也标注了"待确认"，而不是自行填了一个答案？
- 如果原 PRD 有"设计方案文档"作为来源，Spec 的信息是否同时覆盖了设计文档和 PRD 整理稿？设计文档中的架构分层（如调度层/控制层/持久化层/交互层）是否在 Spec 中有所体现？
- **PRD精简的 `specs` frontmatter 是否完整**：所有拆出的 Spec 文件是否都在 `specs` 列表中？`file` 路径是否正确？`summary` 是否覆盖了该 Spec 的关键信息？

---

## 输出格式

两份文档均用 **Markdown** 格式输出：

```
PRD精简_[功能名称].md    ← 面向团队对齐
specs/[功能名称]-[需求点].md  ← 面向 AI 执行
```

### PRD精简的 Spec 清单（frontmatter）

PRD精简必须在其 frontmatter 中记录所有拆出的 Spec 文件路径。这是下游技能（如 TC-generator-ary）检索前置成果的唯一入口，替代手工扫描 Spec 目录。

**格式**：在 PRD精简的 YAML frontmatter 中增加 `specs` 字段：

```yaml
---
title: PRD精简-xxx
specs:
  - 功能名称: "任务提交与调度"
    file: "specs/出库订单波次分配-任务提交与调度.md"
    type: backend
    summary: "提交 API ×2、调度器排序、CAS 校验、重复提交拦截"
  - 功能名称: "异步执行"
    file: "specs/出库订单波次分配-异步执行.md"
    type: backend
