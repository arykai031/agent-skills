# Tester Pipeline

测试用例全流程调度器。不执行具体业务逻辑，只负责判断输入类型、调度子技能、在确认点暂停收集用户反馈、传递阶段产物。

相关技能：`test-devdoc-to-prd`、`test-prd-splitter`、`test-case-generator`、`test-case-md-to-excel`。

## 核心原则

- **不替代子技能**：每个阶段的具体执行完全委托给对应的子技能
- **确认点必须暂停**：任何需要用户确认的环节，停止执行，列出待确认项，等用户回复后继续
- **阶段产物显式传递**：每个阶段产出的文件路径，作为下一个阶段的输入参数传入

---

## 判断：是否需要本调度器

以下场景**不需要**本调度器，直接调用对应子技能：

| 场景 | 直接调用 |
|------|---------|
| 已有结构化 PRD，只需要拆分 | `test-prd-splitter` |
| 已有 PRD精简 + Spec，只需要生成用例 | `test-case-generator` |
| 已有测试用例 Markdown，只需要转 Excel | `test-case-md-to-excel` |
| 只有开发设计文档，只需要翻译成 PRD | `test-devdoc-to-prd` |

以下场景**需要**本调度器：

| 场景 | 执行阶段 |
|------|---------|
| 有原始开发设计文档，要一路生成测试用例 | 阶段零 → 一 → 二 |
| 有结构化 PRD（未拆分），要一路生成测试用例 | 阶段一 → 二 |
| 有原始设计文档，要生成 Excel 测试用例 | 阶段零 → 一 → 二 → 三 |

---

## 阶段零：翻译（test-devdoc-to-prd）

### 触发条件

输入是**原始开发设计文档**（纯技术视角，含类名/代码逻辑/SQL、框架名等），而非结构化 PRD。

判断方法：扫描输入文档，如果出现以下信号 ≥3 个，判定为原始设计文档：
- 类名/包名（如 `AsyncApiTaskExecuteThread`、`IAllocationProgressService`）
- 框架名（如 `XXL-Job`、`Spring`、`MyBatis`）
- SQL 语句或表结构定义（如 `CREATE TABLE`、`ALTER TABLE`）
- 代码级描述（如 `CAS 更新`、`乐观锁`、`Handler`）

### 执行

调用 `test-devdoc-to-prd` 技能，传入原始设计文档路径。

### 产出

- `prd-{功能名}.md`（结构化 PRD，含🚧/📌标记）

### 确认点：🚧 缺口对齐

暂停，输出以下信息：

```
阶段零完成，生成结构化 PRD：{文件路径}

待确认项：
1. 🚧 {缺口描述} → 来源：{章节}
2. 🚧 {缺口描述} → 来源：{章节}
...
📌 推断项：
1. 📌 {推断内容} → 建议验证
...

请与开发确认后回复，格式：
- 已确认：1→{确认内容}
- 已确认：2→{确认内容}
- 暂不处理：3
- 推断正确：📌1
- 推断有误：📌1→{修正内容}
```

用户回复后，按 `test-devdoc-to-prd` Phase 6 的规则更新文档并定稿。定稿后进入阶段一。

### 跳过条件

如果输入已经是结构化 PRD（含 BR/AB 编号、状态码对照表、数据影响表），跳过阶段零，直接进入阶段一。

---

## 阶段一：拆分（test-prd-splitter）

### 触发条件

阶段零已完成（或已跳过），输入为结构化 PRD。如果阶段零未跳过，还需同时传入原始设计文档路径。

### 执行

调用 `test-prd-splitter` 技能，传入：
- 结构化 PRD 路径
- 原始设计文档路径（如果有，test-prd-splitter 会从中提取技术细节）

### 产出

- `PRD精简_{功能名}.md`（含 `specs` frontmatter + 待确认事项表格）
- `specs/{功能名}-{需求点}.md` × N 份

### 确认点：待确认事项

暂停，输出以下信息：

```
阶段一完成，生成：
- PRD精简：{文件路径}
- Spec：{N} 份

PRD精简中的待确认事项：
1. {事项} → 待确认
2. {事项} → 待确认
...

请在 PRD精简中确认后回复"已确认"。
```

### 回写：同步确认结果到 Spec

用户确认后，**由本调度器执行回写**（不交给 `test-case-generator`）：

1. 读取 PRD 精简的"待确认事项"表格，提取每项的确认结果
2. 读取 PRD 精简的 `specs` frontmatter，获取 Spec 清单
3. 逐份读取 Spec，判断哪些受确认结果影响，执行同步

回写规则：

| 确认项类型 | 同步方式 |
|-----------|---------|
| 数据范围变更（如优先级 1-9→1-10） | 更新 Spec 中对应字段的范围描述 |
| 依赖条件确认（如"支持"→ 移除"需补充"） | 更新依赖项表格，移除条件性描述 |
| 策略决策（如"暂不处理"） | 确保 Non-Goals 中已包含该项 |

回写完成后，快速检查所有 Spec 中不再出现"待确认""待补充""需补充""若不支持""若现仅"等标记。

### 阶段二前置门禁：禁止绕过 Spec 回写

进入阶段二前，本调度器必须执行以下门禁检查。**任一项不满足时，禁止调用 `test-case-generator`，必须先完成回写或暂停让用户确认。**

1. PRD 精简中所有待确认事项均已有明确确认结果，不能仅因为用户回复"已确认"就跳过逐项读取。
2. PRD 精简的确认结果已经同步到对应 Spec；测试用例只能基于回写后的 Spec 生成，不能直接基于 PRD 精简中的确认表推导。
3. 对 `specs` frontmatter 中列出的每一份 Spec 执行全文检查，确认不再出现以下未闭环标记：
   - `待确认`
   - `待补充`
   - `需补充`
   - `若不支持`
   - `若现仅`
4. 如果 PRD 精简中仍保留"待确认事项"章节但每项确认结果均为"已确认"，允许保留该章节作为确认记录；但 Spec 中不得保留未闭环标记。
5. 将门禁结果作为阶段二调用说明的一部分传递给 `test-case-generator`：
   - `Spec 已按 PRD 精简确认结果回写完毕`
   - `已检查所有 Spec 无未闭环标记`
   - `跳过 Step 0.1 的确认与同步，直接从 Step 0.2 读取汇总开始`

---

## 阶段二：生成用例（test-case-generator）

### 触发条件

阶段一已完成、确认结果已回写到 Spec，且"阶段二前置门禁"全部通过。此时所有 Spec 已是定稿状态。

### 执行

调用 `test-case-generator` 技能，传入 PRD 精简路径。

**注意**：由于本调度器已在阶段一确认点完成了确认结果到 Spec 的同步，`test-case-generator` 的 Step 0.1.2（检查待确认状态）和 0.1.3（同步确认结果到 Spec）应跳过。在传入参数时告知："Spec 已同步完毕，跳过 Step 0.1 的确认与同步，直接从 Step 0.2 读取汇总开始。"

**禁止行为**：
- 禁止在 PRD 精简已确认但 Spec 未回写时直接生成测试用例。
- 禁止用 PRD 精简确认表临时代替 Spec 定稿内容。
- 禁止生成测试用例后再补做 Spec 回写；如果发生，必须重新基于回写后的 Spec 复核并修正用例。

### 产出

- 测试用例 Markdown 文件（由 `test-case-generator` 的输出规则决定路径和数量）

---

## 阶段三：转 Excel（test-case-md-to-excel）

### 触发条件

用户在阶段二完成后，明确要求生成 Excel。

### 执行

调用 `test-case-md-to-excel` 技能，传入阶段二产出的 Markdown 文件路径。

### 产出

- 测试用例 Excel 文件

---

## 输出汇总

全流程完成后，输出一份简要汇总：

```
全流程完成。

产出文件：
├── 阶段零：{prd文件路径}
├── 阶段一：{PRD精简路径}
│   └── specs/
│       ├── {Spec-1}
│       ├── ...
│       └── {Spec-N}
├── 阶段二：{用例Markdown路径}
└── 阶段三：{用例Excel路径}

确认记录：
- 🚧 缺口 {N} 项已确认
- 待确认事项 {M} 项已回写到 Spec
```
