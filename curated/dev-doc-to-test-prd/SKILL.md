# PRD 转测试需求确认文档

## 概述

将开发视角的技术设计文档（PRD）翻译为测试工程师可读的需求确认文档。核心转换逻辑：从"代码怎么实现"翻译成"什么条件下能做什么、做完后结果是什么"，补充异常边界场景，标记信息缺口。

## 你的工作方式

本技能采用顺序流程，共6个阶段：

1. **阅读提取** — 通读PRD，提取业务规则相关信息
2. **翻译改写** — 按5层结构重新组织，翻译成测试视角
3. **标记缺口** — 标注信息缺口和推断内容
4. **归档交付** — 文件存放+知识库同步
5. **对齐指引** — 输出待确认问题清单，辅助用户与开发对齐
6. **评审定稿** — 用户反馈消化 → 文档更新 → 定稿发布

## Phase 1：阅读提取

通读所有PRD文档，提取业务规则相关的信息。提取原则见 `references/extraction-guide.md`。

关键区分：

- **要提取的**：条件判断、执行逻辑、枚举值、状态变更、字段变更、异常处理、边界值
- **不提取的**：类名/包名、设计模式说明、拦截器原理、SQL语句、部署架构

如果PRD信息严重不足（如只有一段话或只有截图链接），不要跳过，仍创建文档框架，后续用🚧标记缺口。

## Phase 2：翻译改写

按5层结构生成文档，使用 `assets/prd-template.md` 作为模板。

### 5层结构

| 层         | 做什么           | 翻译思路                               |
| ---------- | ---------------- | -------------------------------------- |
| 功能概述   | 一句话说清楚功能 | 从开发目标翻译成用户目标               |
| 业务规则   | 条件→动作→结果   | 从代码逻辑翻译成业务规则表             |
| 状态流转   | 状态怎么变       | 从枚举值和状态变更逻辑翻译成文本流程图 |
| 数据影响   | 哪些字段变了     | 从数据库表设计翻译成变更前后对比表     |
| 异常与边界 | "如果……会怎样"   | 从异常处理代码翻译成冲突/极限场景问题  |

### 粒度控制

文档粒度为**业务规则级**，不写操作步骤。具体来说：

- ✅ 写"只有'部分收货'和'完全收货'状态的单据才能取消"
- ❌ 不写"进入WMS→收货管理→找到单号→点击取消"

### 翻译质量门禁

Phase 2 完成后，**输出前必须逐条自查**以下 4 项——有一项不通过说明翻译改写未完成，回退修改：

1. **❌ 数字状态码**：规则描述中不可出现裸数字码值（如 `1/2/5/6/7`、`status=1`），必须替换为中文状态（如"待执行/处理中/暂停申请中"）；状态流转图可在括号备注码值
2. **❌ 英文变量名**：不可出现 `bizType`、`bizIds`、`taskId`、`progressId` 等代码级命名，必须替换为中文业务术语（如"业务类型"、"单据ID列表"、"任务ID"）
3. **❌ 组件/框架名**：不可出现 `Handler`、`XXL-Job`、`CAS`、`Service` 等直接作为规则主语，必须替换为中文含义（如"分配处理器"、"定时调度任务"、"乐观锁校验"）
4. **✅ 测试可读**：每条规则应能让一名不了解代码的测试人员只看描述就知道"什么条件下、产生什么结果"

### 禁止行为

- ❌ 直接复制代码调用链到输出
- ❌ 出现未被翻译的类名/方法名
- ❌ 出现未被翻译的数字状态码（如 `1/2/5/6/7`）、英文变量名（如 `bizType`）或组件/框架名（如 `XXL-Job`、`CAS`）
- ❌ 加入你自己的推测或未经文档确认的功能假设
- ❌ 删除技术约束条款（即使不好理解也必须保留）

## Phase 3：标记缺口

对PRD中缺失的信息和推断内容进行标记，确保后续对齐时有明确的靶向：

| 标记 | 含义                    | 使用场景                           |
| ---- | ----------------------- | ---------------------------------- |
| 🚧   | PRD中没有，需找开发确认 | 信息缺失、截图无法访问、逻辑不完整 |
| 📌   | 基于业务逻辑推断的内容  | PRD未明确但可推断                  |

标记必须写在表格的"来源"列，两种标记分开，方便用户区分确认重点。

## Phase 4：归档交付

### 文件存放

按功能拆成独立文档，每个功能一个文件。存放位置`{{项目目录}}/需求整理/`

### 文件命名

`prd-{功能名}.md`，功能名使用简短中文描述，如 `prd-质检调整.md`。

## Phase 5：对齐指引

文档生成后，输出一份简要汇总，帮助用户规划开发对齐工作：

1. **🚧密度排序**：按待确认项数量排序，多的优先对齐
2. **📌确认重点**：列出推断内容，提醒用户重点验证
3. **对齐话术**：对异常边界场景，建议用户用"如果……会怎样"的句式跟开发沟通

## Phase 6：评审定稿

用户带着对齐结果回来后，进入评审→修改→定稿的闭环流程。

### 6.1 反馈消化

用户将开发对齐的结果反馈给 Agent，Agent 按以下规则更新文档：

| 反馈类型 | 处理方式 | 标记变化 |
|----------|----------|----------|
| 🚧 已确认 | 将确认内容填入对应表格，删除🚧标记 | 🚧 → 无 |
| 🚧 确认后修改 | 按开发确认的逻辑改写原文，删除🚧 | 🚧 → 无 |
| 📌 已验证正确 | 确认推断正确，删除📌标记 | 📌 → 无 |
| 📌 推断有误 | 按开发纠正的内容改写，删除📌 | 📌 → 无 |
| 新增信息 | 按5层结构补充到对应表格，标注来源 | 🚧新增 → 定稿前需确认 |
| 部分确认 | 更新的内容保留原有标记，未确认的维持不变 | 🚧/📌 保留 |
| 决定暂不处理 | 在来源列标注"已确认暂不处理"，保留原内容 | 🚧 → 已确认暂不处理 |

### 6.2 定稿条件

文档满足以下所有条件后，方可定稿：

| 条件 | 说明 | 例外 |
|------|------|------|
| 所有🚧已关闭 | 每项信息缺口都已确认或明确决定暂不处理 | 经用户确认后可豁免 |
| 所有📌已验证 | 每条推断内容都已核实正确或有修正 | — |
| 无新增未确认信息 | 定稿前最后一轮修改后没有新增未确认项 | — |
| 用户确认定稿 | 用户明确表示文档可以定稿 | — |

### 6.3 定稿发布

满足定稿条件后，执行以下操作：

1. **更新文档状态**：将 Frontmatter 中的 `status` 从 `draft` 改为 `reviewed`（表示已评审通过）
2. **记录定稿信息**：在 Frontmatter 中追加 `reviewed: {date}` 和 `reviewer: {用户或开发人员}`
3. **输出定稿汇总**：简要说明本次定稿涉及的功能、已关闭的🚧/📌数量、以及未纳入定稿的已知限制
4. **知识库同步**：将定稿版文档同步至知识库，覆盖之前草稿版本

### 6.4 定稿后变更

如果定稿后 PRD 发生变更，按以下流程处理：

1. 在原有文档基础上开启新版本，Frontmatter 增加 `version: 2`（逐次递增）
2. 在文档开头追加变更说明，标注"变更内容"和"对应定稿版章节"
3. 仅对变更部分重新执行 5 层结构翻译，未变更部分保持原样
4. 变更内容用🚧标记，重新进入评审→定稿流程

## 工作流示例

### 示例1：信息完整的PRD

用户："帮我把质检调整的PRD转成测试需求文档"

1. 读取PRD-质检调整.md，提取质检判断优先级配置规则、检查策略规则、字段变更
2. 翻译成5层结构：功能概述（配置化质检判断）→ 业务规则（降级匹配7级规则、5种检查类型）→ 状态流转（配置启用/禁用）→ 数据影响（2张新增表）→ 异常边界（6个场景）
3. 标记缺口：🚧头表删除是否级联、🚧同组合是否允许配置多条
4. 输出汇总：5个🚧，建议优先确认配置唯一性约束
5. 用户反馈确认结果后，Agent更新文档：关闭🚧头表删除级联，确认同组合允许配置多条但需校验，将文档status改为reviewed，输出定稿汇总

### 示例2：信息严重不足的PRD

用户："把收货上架拣货作废的PRD也转了"

1. 读取PRD，发现只有一句话"取消收货：只能操作部分收货、完全收货的单"
2. 仍然按5层结构生成框架，大量字段标注🚧
3. 异常边界场景根据WMS通用逻辑（并发、关联数据、事务回滚）列出问题框架
4. 输出汇总：18个🚧，为所有文档中缺口最多的，建议优先与开发对齐
5. 用户分多次反馈对齐结果：Agent 每次根据反馈更新文档、关闭对应🚧，直至所有🚧关闭或确认暂不处理，最终定稿发布
